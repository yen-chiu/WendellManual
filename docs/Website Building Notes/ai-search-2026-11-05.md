## 二、这次改了什么

### 1. Bing HTML 作为中文补充源

- 中文查询（含 CJK 字符）时，与 DuckDuckGo、维基百科**并行**请求 `bing.com/search`。
- 解析 `li.b_algo` 的标题、链接与摘要；Bing 的 `bing.com/ck/a?...` 跳转链会还原成目标地址。
- 结果先做一次**查询词相关性过滤**：标题/摘要必须命中查询里的中文二元组或英文词，避免机房出口偶发的默认页、无关页混进结果。
- **Bing 失败不冷却**：它只是补充源，不能因为它拖慢或阻断主链路。
- 合并时给 Bing 留位置：DDG 前 3 条 + 维基前 2 条 + Bing，再补其余，避免被 5 条 DDG 挤没。

现实情况：从 Cloudflare 机房出口访问 Bing，经常返回空页或无关结果；过滤后为空就静默跳过。所以这个版本里 Bing 是“有机会就补”，不保证每次有产出。

### 2. 5 分钟搜索结果缓存

- 使用 Cloudflare Cache API，按查询词缓存**非空**结果，TTL 300 秒。
- 缓存键带版本号 `v=3`，算法升级时不会读到旧缓存。
- 命中时响应头 `X-Search-Cache: HIT`，响应体多一个 `cached: true`。
- `debug=1` 的请求绕过缓存，方便排查。
- 查询词会以缓存键的形式在边缘节点保留最多 5 分钟，不落数据库。

### 3. 失败分类与引擎冷却

| 失败类别 | 触发条件 | 冷却 |
| --- | --- | --- |
| `bot-wall` | 403、验证码/反爬挑战页、DDG 空壳挑战 | 60 秒 |
| `transient` | 429、5xx、超时、网络错误 | 60 秒 |
| `auth` | 401 | 到当前 isolate 结束 |
| `quota` | 402 | 到当前 isolate 结束 |
| `invalid-response` | 解析失败、0 结果 | 不冷却，只回退 |

- 冷却中的引擎直接跳过，`debug=1` 的 trace 会给出 `failure` 和 `cooldownMs`。
- 冷却只在当前 Worker isolate 内生效；跨实例的全局限流仍建议在 Cloudflare 控制台配置。
- Bing 显式豁免冷却。

## 三、行为变化（对客户端）

1. `/search` 成功响应可能多一个 `bing` 来源（经过滤后）。
2. 命中缓存时多 `cached: true` 与 `X-Search-Cache: HIT`；旧客户端忽略这两个字段即可。
3. 某个源被冷却时，请求会更快落到下一个源，不再反复撞同一个失败源。
4. `debug=1` 仍然绕过缓存和冷却，返回逐源 trace。

## 五、已知限制

- **Bing 不稳定**：机房出口经常空页/无关，过滤后可能一条不剩；需要稳定中文补充时应考虑百度/搜狗 HTML 或付费搜索 API。
- **首次未命中可能慢**：最慢要等上游 8 秒超时；实测有 9.46 秒的一次。可把 `SEARCH_TIMEOUT_MS` 降到 4–5 秒改善。
- **缓存是共享的**：同一查询在 5 分钟内对所有访问者返回同一份结果；不适合搜索敏感内容。
- **冷却不跨实例**：Cloudflare 会回收 isolate，冷却状态随之清空；真正的全局限流在控制台配。
- **Bing 结果过滤是启发式**：中文二元组匹配可能漏掉合理但用词不同的结果。
